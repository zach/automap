## 2. Friction log

Entries are listed in the order they came up. Totals: **content 12, instructions 8, format 4, environment 3** (27 entries).

1. **environment.** The harness loaded `/home/user/automap/CLAUDE.md`, the exploration repo's project instructions, into the agent's context automatically. That file describes the repository layout and working rules, but not the map design. *Resolution:* followed the test rules, read nothing else under `/home/user/automap/`, and relied on nothing from that file. *Change:* run the test agent from a working directory outside the exploration repo, so the repo's instructions don't load.

2. **instructions.** The nevers in `SKILL.md` and `CLI-STEPS.md` disagree. SKILL says "never edit the lock by hand", while CLI-STEPS asks the agent to write the lock by hand and only its own list adds "except by following step 3". SKILL says not to open upstream issues where the policy bans AI contributions, while CLI-STEPS says never open any upstream issues or PRs. *Resolution:* followed CLI-STEPS, as SKILL directs. *Change:* use one list of nevers in both places, and say that in the spike the lock is written by following step 3.

3. **format.** `SKILL.md` step 2 says "Facts and recipes are tied to library versions". In `libraries/*.json`, though, `facts` sits at the top level and not under `versions[]`, so the format can't say which version a fact belongs to. No effect here, because each library has only one version. *Change:* move `facts` under each version, or add a `versions` range to each fact.

4. **content.** The example manifest in `FORMAT.md` (an SDL3 + ImGui composition) has `"determinism": {"enabled": false}`, but no determinism contract exists. It also has `jobs` choices although nothing in that composition binds the jobs contract. *Resolution:* left both out. *Change:* fix the example.

5. **instructions.** `start` takes only `slot=library` pairs, and nothing says how the manifest's `platforms` (and so the compiler and evidence filename) is chosen. The sandbox has both GCC and Clang. *Resolution:* used `linux-x64-clang`, the example's value. *Change:* add `--platform` to `start`, or a documented default derived from the host.

6. **instructions.** Nothing defines which contracts are "in use". That decides which `choices` the manifest carries and which contracts the lock records, and it's unclear whether `platform` counts: no recipe binds it, but its static rule is evaluated. *Resolution:* choices for the bound contracts that have choices (allocation, diagnostics, build-flags, and later jobs); lock `contracts` for every bound contract plus `platform`. *Change:* define "in use" as the contracts of all bindings and pairings, plus contracts whose rules are checked statically.

7. **format.** Manifest `glue` maps each binding to one file path, which doesn't fit three cases here. `dear-imgui/diagnostics` has no glue at all: its reference glue is empty and its rules don't apply, so it was written as `null`. `sdl3/lifecycle` glue lives in the entry point (`main.cpp`). `jolt/jobs` is spread over `jolt_job_system.{h,cpp}` and `jolt_bindings.cpp`, and only one file could be named. *Change:* allow a list of files and an explicit "not applicable" marker with a reason.

8. **instructions.** Start step 4 doesn't say where the composition's `main.cpp` and `CMakeLists.txt` go, or whether binding glue goes flat into `glue/`. *Resolution:* inferred the workspace root and a flat `glue/` from the reference CMakeLists' relative paths. *Change:* state the destination of every copied file.

9. **content.** Every recipe's reference glue includes `automap/probe.h`, and the testbed CMakeLists compiles `glue/automap/probe.cpp`. But `probe.{h,cpp}` is in no contract's `shared_interface.files`, so following step 4 exactly leaves them out and the build fails. *Resolution:* copied them anyway. *Change:* list the probe harness as always-copied in `FORMAT.md` and `CLI-STEPS.md`, or make it a shared interface of its own.

10. **instructions.** Verify step 1 sets no build type or compiler. The build type matters, because Jolt enables `JPH_ENABLE_ASSERTS` only when `NDEBUG` is unset (through `JPH_DEBUG` in `IssueReporting.h`), which decides whether `diagnostics.assert-routed` is probed for Jolt at all. *Resolution:* `-DCMAKE_BUILD_TYPE=Debug` with clang/clang++. *Change:* fix the build type and compilers per platform id, and record them in evidence.

11. **content.** Configure fails with the map's own headless options (`SDL_X11=OFF`, `SDL_WAYLAND=OFF`): "SDL could not find X11 or Wayland development libraries". SDL 3.4 also needs `SDL_UNIX_CONSOLE_BUILD=ON` (SDL's `docs/README-cmake.md`). It is missing from `sdl3.json` `linux_headless_options` and from the reference CMakeLists. *Resolution:* added it to the workspace CMakeLists. *Change:* add it to both.

12. **instructions.** Evidence counting is unclear. "One result per probed rule" could mean per rule or per (rule, library); the CLI doesn't say whether the static `platform.targets-supported` check gives one result per library; and the example "12/12 rules" doesn't fit either reading. *Resolution:* one result per (rule, library), including one static result per library and one `jobs.tsan-clean` result for the composition. *Change:* specify this, and specify the smoke pass criterion (exit code 0, or any clean exit).

13. **content.** The SDL `allocation.hooks-before-first-allocation` probe can never fail. `SDL_GetNumAllocations()` returns -1 unless SDL is compiled with `SDL_TRACK_ALLOCATION_COUNT`, which is commented out in `SDL_malloc.c`, and the glue counts `<= 0` as a pass. A mutation test confirmed it: adding `SDL_SetHint(...)` before `sdl3_bind_allocation()`, the exact mistake the recipe's adaptation note warns against, still gives `"verdict":"pass"`. *Resolution:* recorded it, without strengthening the probe or claiming more than it checks. *Change:* build SDL with `-DSDL_TRACK_ALLOCATION_COUNT` for probe builds, or report "unverifiable" instead of pass on -1. Mutation-test every probe.

14. **content.** `lifecycle.init-order` says steps run "within a phase after the steps they depend on", and the facts carry `after`, but `am::lifecycle::init_order_ok` checks only that phases don't decrease. `after` dependencies are never checked. *Change:* pass the dependency to `init_step` and check it.

15. **format.** SDL's lifecycle facts list `SDL_WaitForGPUIdle` as a platform-phase shutdown step, but the pairing requires it before the systems-phase ImGui backend shutdown. Recording it where it actually runs would fail `lifecycle.shutdown-reverse`, so the reference `main.cpp` doesn't record it, and the probe can't see that ordering. *Change:* let a pairing state cross-library ordering constraints (step X before step Y) and check them.

16. **content.** `dear-imgui.json` has lifecycle facts, but the dear-imgui recipe has no lifecycle binding. Its steps are recorded by the pairing glue instead. Harmless, but an agent checking that every fact has a binding is left unsure. *Change:* add the binding, or note that the pairing covers it.

17. **content.** Probe runs write `imgui.ini` into the developer's repo (the working directory), and later probe runs would load it, so runs aren't independent. *Resolution:* set `io.IniFilename = nullptr` in probe mode in `main.cpp`. *Change:* put this in the testbed reference.

18. **instructions.** Extend step 4 says nothing about the build file, and the map has no reference CMake for adding a library on `extend`; there are only Jolt's `from_source` facts. *Resolution:* wrote the FetchContent block (`SOURCE_SUBDIR Build`, the listed options), checked that `Jolt::Jolt` is an alias in `Jolt/Jolt.cmake`, and added the sources. *Change:* ship a build fragment per library recipe, and make "update the build file" an explicit extend step.

19. **content.** The composition-level jobs wiring has no glue. The adaptation note says to install the shared scheduler in the jobs phase, but nothing creates the `ThreadPool` from the manifest's `workers` choice, names the lifecycle step to record, or says when to uninstall and destroy it. The recipe's `entry_points` keys `jobs-shutdown` and `systems-shutdown` are not phases. *Resolution:* wrote it in `main.cpp` (`ThreadPool(3)`, `install`, lifecycle steps under library `automap`, teardown after `jolt_destroy_job_system()`). *Change:* add composition reference glue for each shared interface's setup, and use `{phase, init|shutdown}` for entry points.

20. **content.** There is no reference glue for the Jolt step every user needs: the systems-phase `TempAllocator` and `PhysicsSystem::Init`, and the three layer interfaces (`BroadPhaseLayerInterface`, `ObjectVsBroadPhaseLayerFilter`, `ObjectLayerPairFilter`). There is also nothing on stepping physics from the game loop. The lifecycle facts name the step, and an adaptation note says "record those steps too". *Resolution:* wrote `falling_sphere.{h,cpp}` from Jolt's `HelloWorld/HelloWorld.cpp`, which needs `GetBroadPhaseLayerName` because `JPH_PROFILE_ENABLED` is on in Debug. *Change:* ship minimal systems-phase reference glue for physics-3d.

21. **content.** Link error: `undefined reference to 'typeinfo for JPH::JobSystemWithBarrier'`. Jolt builds with `-fno-rtti` by default: `CPP_RTTI_ENABLED` is OFF and is applied through its directory's `CMAKE_CXX_FLAGS`, so it isn't propagated. The reference adapter derives from a class whose key function lives in the library. `jolt.json` says only "exceptions_rtti: neither by default", and no note gives the consequence for consumers. *Resolution:* compiled the TUs that include Jolt (`jolt_bindings.cpp`, `jolt_job_system.cpp`, `falling_sphere.cpp`) with `-fno-rtti`. The alternative was building Jolt with `CPP_RTTI_ENABLED=ON`, which changes the library build. *Change:* add a Jolt build-flags adaptation note, and put it in the build fragment. A CI build of the reference glue would have caught this.

22. **content.** The reference adapter has a shutdown race. After a job's barrier is signalled, a worker can still be between `Execute()` and `Release()`, and `Release()` may call `FreeJob()` on the adapter. `jolt_destroy_job_system()` deletes the adapter while the shared scheduler, which outlives it, may still be running that tail: a use-after-free. Jolt's `JobSystemThreadPool` avoids this by joining its threads in its destructor. No probe catches it, because the window is too small for TSAN to see in a 120-frame run. *Resolution:* added an in-flight counter (incremented in `QueueJob`, decremented after `Release()` in `run`), and the adapter's destructor waits for it to reach zero. *Change:* fix the reference glue, and add a probe that destroys the adapter right after an `Update`.

23. **content.** Several Jolt facts are imprecise. `abi_defines` lists `JPH_ENABLE_ASSERTS`, but it's set implicitly by `JPH_DEBUG` (no `NDEBUG`), and the CMake option is `USE_ASSERTS`. The allocation adaptation note ("Jolt allocates from static initializers in some builds only through these hooks once installed") is garbled. `from_source.options` leaves out `JPH_USE_CPU_COMPUTE`, which defaults ON in 5.6 (harmless, plain C++). Jolt's own `ReleaseTSAN` config defines `JPH_DISABLE_CUSTOM_ALLOCATOR`, which would remove the allocation hooks, and nothing warns about it. *Change:* correct these facts.

24. **environment.** The TSAN configure failed: `libclang_rt.tsan-x86_64.a` was not installed for Clang 18 (GCC 13's libtsan was). *Resolution:* `apt-get install -y libclang-rt-18-dev`, the only package installed. *Change:* include it in the sandbox image, and have Verify run a preflight check for the sanitizer runtime.

25. **environment.** The TSAN run as written (only `VK_DRIVER_FILES` set) reports 2 data races in 7 of 7 runs. They are `pthread_mutex_destroy` and `pthread_cond_destroy` against `pthread_mutex_lock` and `pthread_cond_broadcast` on llvmpipe threads, all inside uninstrumented `libvulkan_lvp.so` (Mesa uses futex-based synchronization that TSAN can't see), and they are created under `SDL_CreateGPUDevice`. In a diagnostic run that suppressed only `called_from_lib:libvulkan_lvp.so`, one more third-party report appeared: a lock-order inversion between libLLVM MCJIT and the Vulkan loader. With `LP_NUM_THREADS=0` there were no reports. *Resolution:* used `LP_NUM_THREADS=0` for the evidence run and documented it in `AGENTS.md` and here. No suppressions were used for the evidence. *Change:* see entry 26. Real GPU drivers are uninstrumented too, so this is not only a sandbox problem.

26. **instructions.** `jobs.tsan-clean` and Verify step 3 don't define the TSAN build (C, C++ and linker flags, separate build directory, build type), the run environment, how reports are detected (exit code or log scan), or how to treat reports whose stacks are entirely inside uninstrumented system code such as GPU drivers. Read literally ("no ThreadSanitizer reports"), `extend` stops at **smoke**. *Resolution:* `build-tsan/` with `-fsanitize=thread` in `CMAKE_C_FLAGS`, `CMAKE_CXX_FLAGS` and `CMAKE_EXE_LINKER_FLAGS`, Debug, `TSAN_OPTIONS=exitcode=66`, counting `WARNING: ThreadSanitizer`, `LP_NUM_THREADS=0`, and both readings reported. *Change:* specify all of this, including a per-platform policy for uninstrumented-driver reports: a map-maintained and justified suppression list, or driver settings like `LP_NUM_THREADS=0`, or counting only reports with a frame in composition code.

27. **format.** Evidence can't record the conditions of the run: build type, compiler version, environment variables such as `LP_NUM_THREADS`, TSAN options and suppressions. It also can't record that a rule was not applicable (`diagnostics.*` for dear-imgui) or couldn't really be checked (entry 13). So `probed` claims more than the data supports. *Change:* add a `conditions` object, and a per-result status of `pass`, `fail`, `not-applicable` or `unverifiable`.

## 4. Verdict

**Could an agent reliably do this from the map alone? Not yet.** `start` came close: one wrong fact (`SDL_UNIX_CONSOLE_BUILD`) and one missing file (the probe harness) stop the build. A capable agent fixes both in minutes, but a map-only agent with no access to library source might not. `extend` needed knowledge the map doesn't hold:
- the whole physics-world setup;
- the RTTI link fix, found by reading Jolt's CMake;
- a race fix in the reference adapter;
- a TSAN procedure, plus a judgement call on driver-internal reports that decides whether the result is `probed` or `smoke`.

The probes also gave less assurance than the `probed` label suggests: one probe passes a known-bad mutation, and two ordering constraints are never checked. An agent following the steps exactly gets to "builds" on `start` only after fixing a map bug, and on `extend` either fails to link or ships a latent use-after-free. Even then it has to make an undocumented decision about TSAN.

**Top three changes:**

1. **Build and probe the reference glue in CI, and ship it complete.** That means a build fragment per library recipe (with `SDL_UNIX_CONSOLE_BUILD` and Jolt's `-fno-rtti` consequence), the probe harness as an always-copied file, and composition-level reference glue for `extend`: scheduler setup from choices, and Jolt's systems-phase PhysicsSystem and layer interfaces. One CI run of the two reference compositions would have caught entries 9, 11, 17 and 21. A sanitizer job would have a chance at entry 22.
2. **Make `jobs.tsan-clean` operational.** Give the exact TSAN build and run recipe, how reports are detected, and a written policy for reports wholly inside uninstrumented system code (GPU drivers), such as justified per-platform suppressions or driver settings. Record the run conditions in evidence. Without this, the same composition is `probed` or `smoke` depending on how the agent reads one sentence.
3. **Make probes trustworthy and evidence honest.** Mutation-test every probe: the SDL allocation probe passes a known violation; lifecycle `after` dependencies and the pairing's cross-library ordering are never checked. Let evidence distinguish `pass`, `not-applicable` and `unverifiable`, so `probed` means what it says.
